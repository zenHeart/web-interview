# Interview Question Architect 技能规范

本技能是 Web Interview 题库题目录入、质量评估与答案架构的权威执行标准。用于指导 AI Agent 和贡献者系统性执行“问题收录评估 -> 答案规范架构 -> 自动化合规校验”。

## 一、核心原则与金牌范例

- **黄金标杆范例**：必须严格对齐 [`docs/01.js/01.type-value.md`](/docs/js/type-value)。
- **题库第一性原理（什么才叫面试题）**：
  题库的本质是**面试模拟与能力定级**，绝不是技术手册的章节摘要。严禁生成“知识点拼盘”或“学术论文大纲式”伪题目！
  1. **真实面试口吻原则（Authentic Voice）**：
     题目标题必须符合面试官在现场沟通中能够自然说出口的提问语境。
     - ❌ **反例（学术大纲式）**：`## 大型超万行前端遗留系统（Legacy）架构腐化治理与渐进式重构（Strangler Fig 绞杀者模式）实战？`
     - ✅ **正例（真实面试题）**：`## 面对超万行严重腐化的前端遗留系统，如何用绞杀者模式进行渐进式重构？`
  2. **单一考察职责原则（Single Responsibility Principle, SRP）**：
     每道题必须有且仅有一个聚焦的核心考点。严禁把多个不相关的技术名词用顿号、与、和拼接成知识大杂烩！
     - ❌ **反例（知识点拼盘）**：`## Promise.try()、Promise.withResolvers()、Iterator Helpers 与 Set 集合代数？`
     - ✅ **正例（拆解为独立真题）**：
       - `## Promise.try() 解决了传统 Promise.resolve().then() 的什么痛点？`
       - `## 如何在 Promise 外部触发 resolve / reject？Promise.withResolvers() 是怎么设计的？`
       - `## 原生 Iterator Helpers 相比传统数组 map / filter 链式调用有什么优势？`
       - `## Set 新增了哪些原生集合操作（交集、并集、差集等）？以前是怎么实现的？`
  3. **疑问与情境引导原则（Interrogative & Contextualized）**：
     题目必须包含明确的疑问代词（“为什么”、“如何”、“有什么区别”、“在什么场景下”）或具体的真实代码/情境陷阱（如 `0.1 + 0.2 !== 0.3，为什么，如何解决？`）。严禁在陈述句后简单挂问号作为伪题目。
- **TOC 纯净度铁律**：页面右侧 Table of Contents 仅用于导航具体的面试题（即所有 `## 题目`）。
  - **在 `<Answer>` 标签内部，绝对禁止出现任何级别的 Markdown 标题（`#` 至 `######`）！**
  - 区块分隔必须使用加粗段落文本且以冒号结尾，例如：
    - `**核心结论:**`（或 `**核心概念:**`）
    - `**原理解析:**`（或 `**机制说明:**`）
    - `**示例说明:**`（或 `**规范实现:**`）
    - `**面试官视角:**`
    - `**延伸阅读:**`
- **优先级与 Slug 规范**：ATX 二级标题后挂载严格全小写的 slug，如 `## 题目名称？ {#p0-question-slug}`。

## 二、阶段 A：问题质量评估体系（收录 / 拒绝）

在为任何题目编写答案之前，必须先基于以下两大理论框架进行前置评估。

### 1. 布鲁姆认知分类与知识类别矩阵

| 知识类别 \ 认知层次 | 记忆 (Remember) | 理解 (Understand) | 应用 (Apply) | 分析 (Analyze) | 评价 (Evaluate) | 创造 (Create) |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **事实性知识** (术语/语法) | ❌ 不推荐（纯死记硬背） | ⚠️ 基础热身 | ❌ 不适用 | ❌ 不适用 | ❌ 不适用 | ❌ 不适用 |
| **概念性知识** (模型/原理) | ⚠️ 基础定义 | ✅ 核心机制解释 | ✅ 概念落地场景 | ✅ 异同横向对比 | ✅ 适用边界判断 | ❌ 不创造新概念 |
| **程序性知识** (代码/算法) | ❌ 纯默写语法 | ✅ 代码执行流解释 | ✅ 实现机制与委托 | ✅ 性能与内存诊断 | ✅ 方案重构优化 | ✅ 高效架构设计 |
| **元认知知识** (策略/设计) | ❌ 列举调试工具 | ✅ 理解排查策略 | ✅ 实际定位排错 | ✅ 异步/状态策略 | ✅ 架构方案权衡 | ✅ 创新工程体系 |

- **初级岗位考题**：重点覆盖概念性知识与程序性知识的**理解、应用**层级。
- **高级/资深考题**：必须达到程序性知识与元认知知识的**分析、评价、创造**层级。

### 2. 五大维度质量指标（各维度满分 10 分，需全部 >= 6 分才予以收录）

1. **有效性（Validity）**：能否准确评估真实开发能力，杜绝与岗位无关的冷知识（如背诵 HTTP 私有状态码）。
2. **信度（Reliability）**：是否有明确评分 Rubric，减少面试官主观偏见。
3. **区分度（Discrimination）**：阶梯式难度，初级能答要点，高手能深入底层原理与机制权衡。
4. **时间合理性（Efficiency）**：适合在 5~30 分钟内完成高密度技术交流，非无意义大项目耗时。
5. **贴近实际（Relevance）**：符合工业级生产工程真实场景，拒绝脱节的纯学术题目。

### 3. 评估输出格式（简化 Rubric 表格）

```markdown
### 题目：<原题目标题>

| 维度 | 得分 (1-10) | 结果 | 说明 |
| :--- | :--- | :--- | :--- |
| 有效性 (Validity) | 9 | ✅ | 准确考察生产级核心机制 |
| 信度 (Reliability) | 8 | ✅ | 评分 Rubric 要点清晰 |
| 区分度 (Discrimination) | 9 | ✅ | 能拉开初级与高级架构见解差距 |
| 时间合理性 (Efficiency) | 9 | ✅ | 10-15 分钟适中 |
| 贴近实际 (Relevance) | 9 | ✅ | 贴近微前端与状态持久化真实痛点 |

**收录结论**：✅ 予以收录 / ❌ 拒绝收录
**理由说明**：<一句话简述理由或最小改写建议>
```

## 三、阶段 B：答案金字塔架构规范

仅对收录的题目编写答案，且答案必须满足以下契约：

1. **容器标签**：使用 `<Answer>` 和 `</Answer>` 包裹，标签不加任何多余属性。
2. **区块组织**：
   - **`**核心结论:**`**：直给 2~4 条核心要点，拒绝废话。
   - **`**原理解析:**`**：机制推导、架构流程图（Mermaid）、底层算法分析。
   - **`**规范实现 / 示例说明:**`**：
     - 能运行代码绝不用静态纯文本；
     - 复杂系统设计优先使用已有 Visualizer 组件（如 `<StranglerVisualizer />` 等）；
     - API/代码逻辑题优先使用 `<CustomSandPack template="node|react|static" />` 或 `<TestCode />`；
     - 导入必须使用 `import X from '!!raw-loader!./answers/xxx'`，且 `files` 路径必须以 `/` 开头并保持一致。
   - **`**面试官视角:**`**：
     - 评分 Rubric：要点清单（必答）、加分项（高阶思考）、常见误区/失误。
   - **`**延伸阅读:**`**：
     - 优先提供官方标准规范（ECMA-262 / WHATWG / W3C / MDN）及一句话解析。
3. **字数与节奏**：精炼在 300~800 字（不含组件代码），结构紧凑。

## 四、MDX v3 兼容性与静态语法看门狗

必须 100% 遵守以下铁律以确保构建 0 错误：
- **严禁未转义小于号**：小于号后紧跟数字或表达式必须转义或加空格，如 `< 100ms` 或 `小于 100ms`，严禁写为 `<100ms`。
- **严禁反引号中裸写模板占位符**：Markdown 反引号代码中不可出现未转义的 `${...}`。
- **严禁行内裸写 LaTeX 大括号**：数学公式需使用行内代码 `` 或 KaTeX `$` 对称包裹，严禁在正文中裸写 `\text{...}`。
