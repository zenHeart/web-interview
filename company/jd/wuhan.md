## 题库

### P0 必考知识点

#### 多 Tab 页大型 Electron 桌面应用内存持续暴涨如何做深度优化？ {#p0-electron-multi-tab-memory}

<Answer>

### 核心结论

Electron 应用每个打开的窗口或 Tab 页默认由独立的 Chromium 渲染进程承载。若商家同时打开 20+ 个商品和订单 Tab，内存极易突破 2GB 导致崩溃。业界（如腾讯文档、新版 QQ、京东京麦）成熟解决方案是**单渲染进程多视图复用 + 非激活 Tab 挂起冻结（Tab Hibernation） + IPC 零拷贝通信 + 周期性垃圾回收 GC 触发**。

---

### 关键优化实践

1. **WebContentsView 替代独立 BrowserView/Window**：
   - 避免每个 Tab 创建一个沉重的操作系统原生窗口，改用轻量级的视图容器复用渲染管线。
2. **Tab 挂起冻结与 DOM 虚拟休眠（Hibernation）**：
   - 当某个 Tab 处于非激活后台状态超过 5 分钟：
     1. 将该 Tab 的当前状态与数据持久化至 IndexedDB 或内存快照；
     2. 销毁当前 Tab 的真实 DOM 树与 Canvas 上下文，将其导航至轻量级空白占位页（`about:blank`）或释放对应 WebContents；
     3. 用户重新点击激活该 Tab 时，微秒级从快照恢复渲染。
3. **主进程与渲染进程 IPC 通信优化**：
   - 严禁通过 `ipcRenderer.send` 频繁序列化传输超大 JSON（造成 V8 堆内存激增）；
   - 改用基于 `SharedArrayBuffer` 或内存映射（Memory-Mapped Files）进行进程间零拷贝共享。
4. **内存泄漏监控与白屏自动容灾**：
   - 监听渲染进程崩溃事件 `render-process-gone`，自动触发无感静默拉起与现场恢复。

#### 基于 Electron 的桌面端自动化操作与插件基建如何设计？ {#p0-electron-desktop-automation}

<Answer>

### 核心结论

在电商商家客服与自动发货场景中，需模拟键盘输入、鼠标点击与桌面窗口控制。架构设计核心是**主进程安全守护 + Node.js 原生 C++ Addon（如 Node-RobotJS）执行底层系统 API 调用 + 预加载脚本（preload.js）白名单 RPC 桥接**。

---

### 架构设计维度

1. **上下文隔离（contextIsolation: true）与安全 RPC**：
   - 渲染进程严禁开启 `nodeIntegration: true`，防止第三方网页 XSS 获得操作系统任意代码执行权限。
   - 在 `preload.js` 中使用 `contextBridge.exposeInMainWorld` 暴露受限的自动化操作命令（如 `window.desktopAPI.simulateClick(x, y)`）。
2. **底层 C++ 模拟实现**：
   - 通过 Node 原生模块封装 Windows Win32 API（`SendInput`, `SetForegroundWindow`）与 macOS CGEvent，精准控制外设事件分发。
3. **任务队列与防并发冲突调度**：
   - 自动化流程可能涉及多步骤连贯动作（打开窗口 → 等待加载 → 聚焦输入框 → 打字）。
   - 在主进程维护异步任务队列（Action Queue），保证任务原子性与超时中断恢复。
