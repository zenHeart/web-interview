浏览器常见事件在事件循环中的相对顺序（示意）

备注：HTML 标准并未为所有事件定义 硬编码的数值优先级，而是通过“任务源”与“事件循环阶段”间接决定执行时机。下表是主流浏览器（Chromium / WebKit / Gecko）常见、可观察到的典型顺序示意。

阶段/类别(概念)典型来源触发时机（相对）说明
宏任务(Task)script(初始)、setTimeout / setInterval、postMessage、MessageChannel、部分事件回调事件循环每轮开始时取 1 个执行完后会刷新微任务队列
微任务(Microtask)Promise.then / queueMicrotask / MutationObserver当前宏任务结束后、渲染前；若产生新微任务会继续清空不要长时间阻塞，影响渲染/输入
用户输入事件click / pointer / key / wheel通常在上轮渲染后，下轮脚本前被派发；部分实现为减少输入延迟会提早处理高优先级感知，可能打断空闲回调
requestAnimationFramerAF 回调渲染前一帧合成阶段对动画/测量布局友好
渲染/合成样式计算、布局、绘制、合成宏任务 & 微任务清空后若主线程长任务阻塞会延迟
requestIdleCallbackrIC 回调一帧渲染完成且有剩余空闲片段可能被饿死，不保证执行

关键要点

  • 事件循环一轮：取一个 宏任务 → 执行 → 清空全部 微任务 → 可能进行渲染（若需要）→ rAF → rIC。
  • Promise.then / queueMicrotask / MutationObserver 都在微任务阶段，内部先入先出（同源队列）。
  • requestAnimationFrame 早于渲染提交，用于读取最新布局并写入动画。
  • 输入事件常在渲染后派发，但浏览器会为低延迟输入作策略调整（不保证严格顺序）。
  • requestIdleCallback 仅在帧剩余时间大于阈值（典型 50ms 预算之剩余）才执行。

常见误区

  
    
    
  • 微任务不是“更高优先级的一类任务”，只是当前宏任务结束后立刻清空，它不会打断正在执行的宏任务。
    • 
    
  • requestAnimationFrame 不是微任务；它在下一帧渲染前统一回调。
    • 
    
  • 不同浏览器对输入事件提早派发、合并策略可能不一致，因此不要依赖“输入事件绝对早于 timeout”。
    • 
    
  • requestIdleCallback 没有执行保证，低性能设备或主线程繁忙时可能长期不触发。
    • 
  


  
总结（面试表达示例）

  

    简述：浏览器事件循环每轮取一个宏任务执行，期间排入的微任务在该宏任务结束后一次性清空，随后进行渲染前的 rAF 回调，再进入渲染/合成，最后若时间有余执行空闲回调。Promise/queueMicrotask 属于微任务；setTimeout 属于宏任务；rAF 在渲染前；用户输入事件通常在上一帧渲染后、下一帧脚本前注入。理解这一顺序有助于优化动画流畅度、避免长任务阻塞与微任务“饿死”渲染。
