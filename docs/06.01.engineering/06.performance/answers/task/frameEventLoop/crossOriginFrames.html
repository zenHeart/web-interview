不同“域上下文” iframe 对事件循环影响示例

演示 同源 iframe 与一个 沙箱(opaque origin) iframe（通过 sandbox 去掉 allow-same-origin，模拟不可访问的跨源上下文）之间的调度与阻塞差异。真实浏览器中跨站点 iframe 可能运行在独立进程；此处用 sandbox + postMessage 近似说明：

  • 两个 iframe 各自执行：同步代码 → 微任务(Promise/queueMicrotask) → 宏任务(setTimeout)
  • 它们向父页面 postMessage 发送：内部时间戳、阶段类型
  • 父页面可选择执行一次 长阻塞任务，比较“发送时间(sent)”与“接收时间(received)”的差值

解读

  
    
    
  • 若看到 sandbox iframe 的 sent 时间早于父页面解除阻塞，但父页面的 received 时间延后，说明：iframe 自身线程(或任务队列)已完成调度，但父页面事件循环被阻塞，消息处理延迟。
    • 
    
  • 真实跨站点 + 不同渲染进程时，父页面阻塞不影响 iframe 内部计时推进，但消息派发到父页面的回调仍需等待父页面主线程空闲。
    • 
    
  • 这说明“是否独立进程”影响 内部执行；而 postMessage 的回调总在接收方事件循环空闲后执行。
    • 
  

  
面试要点

  
跨域(跨站点) iframe 可能获得独立进程以隔离故障与提升并行，但不会改变 Web 事件循环语义：消息 / 回调在接收上下文排队等待。判断是否独立主要看：① 是否能访问 DOM ② 性能剖析里是否出现独立进程 / 线程 ③ 阻塞父页面时 iframe 内计时是否继续推进。
