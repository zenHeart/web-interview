协议生态与质量工程 (Protocols & Ecosystem) ✅

本模块系统性梳理大模型前端工程生态链、开放协议与质量治理体系：跨工具通用标准协议 Model Context Protocol (MCP)、Agent 间互操作协议 A2A (Agent2Agent)、AI 辅助编程代码质量门禁与防幻觉机制、规格驱动开发（Spec-Driven Development, SDD）架构闭环以及大模型与 Agent 自动化量化评测体系（Eval Benchmark）、Skill 路由准确率的可量化评测方法与 ASR 转写指标（WER）与下游任务指标的错位诊断。

Model Context Protocol (MCP) 协议在前端是如何工作的？它与传统 Function Calling 有什么区别？​

答案

核心结论:

Model Context Protocol (MCP) 是由 Anthropic 牵头开源的大模型上下文开放协议标准，旨在终结过去不同大模型平台私有 Function Calling（工具调用）硬编码生态割裂的局面，成为大模型时代的“USB-C 接口”：

  • 解耦模型与工具：传统 Function Calling 需要宿主将所有可用工具的 JSON Schema 硬编码写死在单次请求的 Payload 中，模型每换一个平台或工具更新就需要改动核心代码；MCP 抽象出标准的 Host（宿主）- Client（客户端）- Server（能力服务端） 三层架构；
  • 核心能力三要素：MCP 统一规范了三大基准能力：
    1. Tools（工具）：具有副作用的动作执行器（Actionable Functions），支持动态发现与参数校验；
    2. Resources（上下文资源）：只读数据文件/知识文档（如本地文件、数据库记录、API Schema），供模型挂载检索；
    3. Prompts（提示词模板）：预设的工作流模板与角色指导；
  • 前端定位：在桌面前端（Electron / Tauri / VS Code 插件）或 Web 浏览器中，前端通常作为 MCP Host 运行 MCP Client 实例，通过 stdio（子进程）或 SSE / Streamable HTTP（远程网络服务）与本地/云端各类 MCP Server 建立动态双向 RPC 通信。

原理解析:

1. 传统 Function Calling vs MCP 架构对比

对比维度传统 Function Calling (如 OpenAI Tools)Model Context Protocol (MCP)
架构耦合度强耦合。前端需硬编码定义全部工具 Schema 并注入请求体解耦。客户端动态向 MCP Server 发现（tools/list）并注册
生态扩展性每新增一个工具需重新部署核心业务代码即插即用。用户添加 MCP Server 配置即可无缝扩充能力
通信协议无独立协议，依赖各大厂商各自私有的 REST API 规范标准 JSON-RPC 2.0 协议规范（跨语言、跨传输层统一）
支持能力范围仅支持可执行函数（Tool Execution）涵盖 Tools（调用）、Resources（数据）与 Prompts（模版）
传输通道仅限 HTTP POST Payload支持 Local Stdio（进程输入输出）、SSE、WebSockets 等
权限与安全隔离权限由后端集中托管，前端感知弱支持细粒度的 Client 授权批准门禁与本地进程沙箱隔离

2. MCP 客户端-服务端协议调用拓扑

3. 前端集成 MCP 的核心工作流（以 2026-07-28 规范为准）

  1. 能力发现（Discovery）：Client 可先调用 server/discover 一次性拿到 Server 支持的协议版本、Capabilities 与身份信息；随后用 tools/list 与 resources/list 动态获取工具清单及对应 JSON Schema；
  2. 无状态请求（Stateless）：2026-07-28 起取消了 initialize / notifications/initialized 握手，每个请求都要在 _meta 中携带 io.modelcontextprotocol/protocolVersion 与 io.modelcontextprotocol/clientCapabilities；
  3. 动态 Schema 注入：前端将发现的 MCP 工具 Schema 转换为大模型支持的 Tool 格式，注入对话上下文；
  4. 模型决策与 RPC 派发：模型触发工具调用时，MCP Client 拦截请求，解析出目标 MCP Server 名称及工具参数，发起 tools/call RPC 请求；
  5. 执行与安全门禁：若工具标注为危险操作，MCP Client 挂起执行，唤起前端授权弹窗；获批后将真实调用结果回传给大模型；
  6. 多轮往返（MRTR）：当 Server 需要客户端补充信息（如授权确认）时，返回 resultType: "input_required" 的中间结果并携带 inputRequests，客户端在重试原请求时用 inputResponses 回填——这取代了旧版由服务端主动发起 elicitation/create 的写法。

版本要点（易错）：MCP 协议版本历史为 2024-11-05 → 2025-03-26 → 2025-06-18 → 2025-11-25 → 2026-07-28，当前生效版本为 2026-07-28。该版本移除协议级 session 与 Mcp-Session-Id、移除握手、移除 ping / logging/setLevel，并把 Roots / Sampling / Logging 标记为 Deprecated（最早移除时间为 2027-07-28 之后的首个修订）；tasks 也从核心协议移出，改为官方扩展 io.modelcontextprotocol/tasks。新实现不应再使用「客户端通过 sampling/createMessage 向服务端请求补全」这类旧写法。

规范代码实现:

以下为前端基于 TypeScript 实现的轻量标准 MCP 客户端核心（JSON-RPC 2.0 消息抽象与工具调用协议调度）：

// mcp/types.ts
export interface JsonRpcRequest<T = Record<string, unknown>> {
  jsonrpc: '2.0';
  id: string | number;
  method: string;
  params?: T;
}

export interface JsonRpcResponse<T = unknown> {
  jsonrpc: '2.0';
  id: string | number;
  result?: T;
  error?: {
    code: number;
    message: string;
    data?: unknown;
  };
}

export interface McpToolSchema {
  name: string;
  description?: string;
  inputSchema: {
    type: 'object';
    properties: Record<string, unknown>;
    required?: string[];
  };
}

// mcp/client.ts
export interface IMcpTransport {
  send(message: JsonRpcRequest): Promise<void>;
  onMessage(handler: (message: JsonRpcResponse) => void): void;
  close(): Promise<void>;
}

export class McpClient {
  private transport: IMcpTransport;
  private pendingRequests = new Map<string | number, {
    resolve: (value: unknown) => void;
    reject: (reason: unknown) => void;
  }>();
  private requestId = 0;
  private cachedTools: McpToolSchema[] = [];

  constructor(transport: IMcpTransport) {
    this.transport = transport;
    this.transport.onMessage(this.handleIncomingMessage.bind(this));
  }

  private handleIncomingMessage(res: JsonRpcResponse): void {
    const handler = this.pendingRequests.get(res.id);
    if (!handler) return;

    this.pendingRequests.delete(res.id);
    if (res.error) {
      handler.reject(new Error(`MCP RPC Error [${res.error.code}]: ${res.error.message}`));
    } else {
      handler.resolve(res.result);
    }
  }

  private sendRpc<T>(
    method: string,
    params?: Record<string, unknown>,
    opts?: { meta?: Record<string, unknown> }
  ): Promise<T> {
    const id = ++this.requestId;
    const request: JsonRpcRequest = {
      jsonrpc: '2.0',
      id,
      method,
      params: opts?.meta ? { ...params, _meta: opts.meta } : params,
    };

    return new Promise((resolve, reject) => {
      this.pendingRequests.set(id, { resolve: resolve as (v: unknown) => void, reject });
      this.transport.send(request).catch(reject);
    });
  }

  // 1. 无状态请求元信息（2026-07-28 起取代 initialize 握手）
  // 协议版本历史（以 modelcontextprotocol/specification 仓的 schema 目录为准）：
  //   2024-11-05 -> 2025-03-26 -> 2025-06-18 -> 2025-11-25 -> 2026-07-28
  // 2026-07-28 关键变更：移除 initialize 握手与协议级 session；
  // Roots / Sampling / Logging 标记 Deprecated；
  // tasks 移出核心协议，改为官方扩展 io.modelcontextprotocol/tasks；
  // 服务端发起请求改为 MRTR（多轮往返）模式。
  private buildMeta(): Record<string, unknown> {
    return {
      'io.modelcontextprotocol/protocolVersion': '2026-07-28',
      'io.modelcontextprotocol/clientCapabilities': {
        extensions: {}, // 2026-07-28 新增：声明对官方扩展的支持
      },
      'io.modelcontextprotocol/clientInfo': {
        name: 'web-interview-mcp-client',
        version: '1.0.0',
      },
    };
  }

  // 2. 能力发现：Server MUST 实现 server/discover
  public async discover(): Promise<{ protocolVersions: string[]; capabilities: Record<string, unknown> }> {
    return await this.sendRpc('server/discover', {}, { meta: this.buildMeta() });
  }

  // 3. 动态发现工具清单（2026-07-28 要求确定性返回顺序，以利 Prompt Cache 命中）
  public async listTools(): Promise<McpToolSchema[]> {
    const response = await this.sendRpc<{ tools: McpToolSchema[] }>('tools/list', {}, { meta: this.buildMeta() });
    this.cachedTools = response.tools;
    return this.cachedTools;
  }

  // 4. 执行特定工具；结果必带 resultType（complete / input_required）
  public async callTool(toolName: string, args: Record<string, unknown>): Promise<unknown> {
    return await this.sendRpc('tools/call', { name: toolName, arguments: args }, { meta: this.buildMeta() });
  }
}

MRTR 的处理方式：当 resultType 为 input_required 时，服务端会在 inputRequests 里带上它需要的信息（例如授权确认）。客户端完成交互后，重试原请求并在 inputResponses 中回填，而不是让服务端主动发起 elicitation/create。

团队引入 Cursor / Copilot / Claude Code 后，如何建立代码质量门禁（Quality Gate）与防范幻觉？​

答案

核心结论:

在研发团队全员引入 Cursor、Copilot、Claude Code 等 AI 编程助手后，虽然整体代码产出速度提升了 30%~50%，但同时也引入了三大隐蔽工程风险：

  1. API 虚构与幻觉（Hallucination）：模型频繁使用已被废弃（Deprecated）或凭空捏造的私有方法；
  2. 代码风格与架构模式漂移：缺少全局架构感知的碎片化生成导致圈复杂度飙升、类型注解退化为 any；
  3. 安全漏洞与凭证泄露：模型在补全时可能引入未校验的输入注入漏洞，甚至误将开发者的本地 Token 写入代码； 因此，建立一套端到端的四层质量纵深防御门禁（Quality Gate）是防止代码库快速腐化的关键护城河。

原理解析:

1. AI 编程代码质量四层纵深防御拓扑

2. 核心防御机制拆解

  • Layer 1: IDE 实时约束与上下文供给：
    • 在项目根目录维护 .cursorrules、CLAUDE.md 或统一的 Agent 规则清单，明确规定技术栈版本（如 Vue 3.5 / React 19 / Vite 8）、禁止使用的库（如禁用 Moment.js）、代码结构规范。从源头缩小大模型的采样空间，抑制幻觉产生；
  • Layer 2: Git Hook 增量安全卡口：
    • 通过 lint-staged 对暂存区变更文件执行严格类型检查与 ESLint 校验；同时引入开源工具（如 gitleaks）拦截任何匹配 AWS Key、OpenAI Token、私钥特征的文本提交；
  • Layer 3: CI/CD 绝对确定性自动化卡点：
    • 大模型生成的单元测试常常存在“为了通过测试而伪造断言（Trivial Assertions）”的欺骗行为。CI 流水线必须执行真实的突变测试（Mutation Testing）并设置刚性代码覆盖率阈值（如核心业务行覆盖率必须大于等于 80%）；若未通过，直接阻断合并权限；
  • Layer 4: AI 初审 + 人工关键决策：
    • 接入自动化 AI Review 机器人（如 CodeRabbit、GitHub Copilot PR Reviewer），在 PR 提交后 30 秒内完成常规排版、潜在边界溢出初筛；人类工程师将精力聚焦于核心业务逻辑与数据流向设计。

什么是 Spec-Driven Development (SDD)？如何通过规则资产库约束大模型生成符合架构的代码？​

答案

核心结论:

Spec-Driven Development（SDD，规格驱动开发） 是企业级研发团队让大模型从“非确定性概率生成玩具”演变为“生产级工业软件工程”的核心范式跃迁：

  • 从 Prompt Engineering 到 Spec Enforcement：口头或自然语言提示词（Prompt）具有天然的歧义性与不稳定性；SDD 强调契约与规格先行——在让大模型编写一行业务实现代码之前，必须先确立严谨完备的机器可读规格（OpenAPI 规范、TypeScript 类型契约、JSON Schema、设计系统 Token、ADR 架构决策记录）；
  • 系统上下文强注入（Context Grounding）：将这些 Spec 转换为标准化的结构化规则资产（Rules / Schemas），在调用大模型时作为 System Context 强约束其自由度，使模型只能在既定的类型边界与接口定义内“做填空题”；
  • 自闭环纠错（Self-Correction Loop）：若模型生成代码违反 Spec，编译器与类型检查器输出的精准报错信息直接作为反馈注入下一轮推理，直至 100% 满足规格才被接纳。

原理解析:

1. 规格驱动开发（SDD）自闭环生成架构

2. 企业级规则资产库（Rules Asset Hub）三层拓扑

  1. 底层平台基线（Platform Baseline）：
    • 全局编码规范、安全基线、性能门槛、禁用的旧 API 映射表（如全局禁止使用 localStorage 存敏感数据，必须走统一加密存储服务）；
  2. 领域架构契约（Domain Architecture Contracts）：
    • 包含业务领域核心 Entity、聚合根类型定义、全局错误码枚举。大模型生成代码必须直接 import 权威契约，不允许在业务组件中私自 duplicate 类型；
  3. 任务级执行清单（Task-Level Execution Plan）：
    • 将大型任务分解为有序细粒度的步骤清单（Checklist），每一步要求模型仅修改指定文件并产出对应验证指令，杜绝模型产生“大跨步幻觉”。

规范代码实现:

以下为生产级架构中，基于 TypeScript 实现的自动化“规格校验-自我纠错”执行器核心：

// sdd/self-correction-runner.ts
import { exec } from 'node:child_process';
import { promisify } from 'node:util';

const execAsync = promisify(exec);

export interface GenerationTask {
  taskId: string;
  specFiles: string[]; // 权威接口契约文件路径
  targetFile: string;
  prompt: string;
}

export class SpecDrivenCodeGenerator {
  private maxRetries = 3;

  // 1. 模拟调用 LLM (实际调用 Claude / GPT-4o / 本地模型)
  private async callLlm(prompt: string, errorContext?: string): Promise<string> {
    let finalPrompt = prompt;
    if (errorContext) {
      finalPrompt += `

【上轮生成代码静态类型校验失败，请针对以下报错精准修复，严禁变更接口契约】:
${errorContext}`;
    }
    // 返回模型生成的代码内容...

// eval/eval-judge-runner.ts
export interface TestCase {
  id: string;
  query: string;
  context: string;
  groundTruth: string;
}

export interface EvalResult {
  testId: string;
  score: number; // 1 ~ 5 分
  passed: boolean;
  critique: string; // 裁判模型的评语
}

export class LlmJudgeEvaluator {
  // 结构化评测打分细则 (Evaluation Rubric)
  private evaluationRubric = `
你是一名极其严格的 AI 输出质量评估专家。请根据以下维度对【模型回答】进行 1 到 5 分的综合量化评分：
- 5分（卓越）：回答完全忠实于参考上下文，无任何虚构事实，逻辑清晰且彻底解决了用户问题；
- 4分（良好）：回答准确，解决了核心诉求，但在措辞或细节上有极其轻微的不完善；
- 3分（及格）：回答基本正确，但遗漏了关键要点，或者包含了模糊表述；
- 2分（不及格）：包含明显的事实性幻觉，或者遗漏了核心必须信息；
- 1分（完全不可用）：完全脱离上下文胡编乱造，或者严重答非所问。

输出格式要求：请严格返回 JSON 格式，包含 "score"（数字 1-5）和 "critique"（简短评析原因）。
`;

  // 调用高阶裁决模型 (如 GPT-4o 或 Claude 3.5 Sonnet)
  private async callJudgeModel(prompt: string): Promise<{ score: number; critique: string }> {
    // 模拟裁判模型返回 JSON 评测结果
    return {
      score: 5,
      critique: '模型回答完全忠实于参考切片，且结构化罗列了所有要点，无任何多余幻觉。',
    };
  }

  public async evaluateCase(testCase: TestCase, actualOutput: string): Promise<EvalResult> {
    const judgePrompt = `
${this.evaluationRubric}

【用户问题】: ${testCase.query}
【参考上下文】: ${testCase.context}
【黄金参考答案】: ${testCase.groundTruth}
【待评测的模型回答】: ${actualOutput}
`;

    const judgment = await this.callJudgeModel(judgePrompt);

    return {
      testId: testCase.id,
      score: judgment.score,
      passed: judgment.score >= 4,
      critique: judgment.critique,
    };
  }

  // 批量运行基准测试集并计算整体通过率
  public async runBenchmark(testCases: TestCase[], outputs: Map<string, string>): Promise<{
    total: number;
    passRate: number;
    avgScore: number;
    failures: EvalResult[];
  }> {
    const results: EvalResult[] = [];

    for (const testCase of testCases) {
      const output = outputs.get(testCase.id) || '';
      const result = await this.evaluateCase(testCase, output);
      results.push(result);
    }

    const passedCount = results.filter((r) => r.passed).length;
    const avgScore = results.reduce((sum, r) => sum + r.score, 0) / results.length;
    const failures = results.filter((r) => !r.passed);

    return {
      total: testCases.length,
      passRate: (passedCount / testCases.length) * 100,
      avgScore,
      failures,
    };
  }
}

线上真实 bad case 怎么自动回流成评测集？修好一类之后怎么发现其他场景退化了？​

答案

核心结论:

评测集不是「攒出来的题库」，而是线上失败的一级缓存。没有回流机制的评测体系，测的永远是你已经知道的那批问题。

完整闭环是四步：

  1. 采集：线上 Trace 里的失败样本（用户点踩、工具执行报错、任务未完成、人工介入、结果被下游打回）自动落成一个 bad case 候选池；
  2. 归因与去重：区分「模型能力不足」与「Harness/工具/数据问题」——后者不该进评测集（它不是模型该背的锅），前者才进入候选；
  3. 定级与标注：按「影响面 × 复现稳定性」定级（P0 阻断 / P1 回归 / P2 观察），人工只标注 P0/P1，其余走自动聚类与规则筛；
  4. 沉淀与守护：晋升为 Golden Case 后进入回归集，每次发布前全量跑；并同时维护「覆盖度视图」，否则只能发现「修好了」，发现不了「修坏了别处」。

发现退化的三种手段（缺一不可）：

  • 全量回归：固定评测集全量跑，比对每个用例的前后结果，而不是只看总分；
  • 差异切片（Diff Slicing）：把总用例按维度（任务类型 / 工具 / 输入形态 / 长度档位）切片，只对发生变化的切片报警，避免「平均分没动」掩盖局部崩塌；
  • 不变量（Invariant）检查：为每类任务定义必须成立的性质（如「不得输出未在上下文中出现的字段」「调用写工具前必须有确认」），用规则断言而非人工判分来发现退化。

原理解析:

1. 回流链路

2. 为什么「只看总分」发现不了退化

改一个 Prompt 让 A 类任务从 80% 涨到 95%、B 类任务从 90% 掉到 70%，总分几乎不动，但线上体验是灾难。评测必须能定位到「哪一类变差了」，这要求用例集本身带维度标签（任务类型、涉及工具、输入形态、难度档），而多数团队的评测集只是一堆没有标签的 prompt。

3. 自动标注的现实边界

「答案自动标注」目前只能做弱监督：用规则与启发式（是否触发了必需工具、输出是否满足 Schema、是否命中禁用词、是否需要人工介入）产出一个粗标签，用来排序候选和发现长尾，不能直接当作 Ground Truth 进回归集。真正的 Golden Set 必须有人工签字，否则回归集会被噪声污染，团队很快就会因为「指标一直抖」而放弃门禁。

4. 覆盖度视图要回答三个问题

  • 空间覆盖：哪些任务类型 / 工具 / 难度档在评测集里根本没有任何用例？（空白区往往正是线上问题高发区）
  • 分布覆盖：评测集的分布与线上真实流量分布差多少？（全测简单样本会让指标虚高）
  • 时效覆盖：最近三个月线上新增的任务形态，是否已进入评测集？

// 2) 归因：工程问题不进评测集，避免让模型背工程的锅
export function triage(samples: TraceSample[]): { toEval: TraceSample[]; toTickets: TraceSample[] } {
  const toEval: TraceSample[] = [];
  const toTickets: TraceSample[] = [];
  for (const s of samples) {
    if (s.rootCauseHint === 'tool-defect' || s.rootCauseHint === 'data-quality' || s.rootCauseHint === 'env-flaky') {
      toTickets.push(s);
    } else {
      toEval.push(s);
    }
  }
  return { toEval, toTickets };
}

// 3) 切片差异：只对发生变化的切片报警，而不是看总分
export function diffSlices(
  before: Map<string, number>,
  after: Map<string, number>,
  dropThreshold = 0.05
): Array<{ slice: string; delta: number }> {
  const drops: Array<{ slice: string; delta: number }> = [];
  for (const [slice, beforeRate] of before) {
    const afterRate = after.get(slice) ?? 0;
    if (beforeRate - afterRate > dropThreshold) drops.push({ slice, delta: beforeRate - afterRate });
  }
  return drops.sort((a, b) => b.delta - a.delta);
}

// 4) 不变量：规则化发现退化，比人工判分稳定得多
export function checkInvariants(c: EvalCase, output: unknown): string[] {
  return c.invariants
    .map((fn, i) => (fn(output) ? null : `invariant#${i} violated`))
    .filter((x): x is string => x !== null);
}

为什么让 Agent 自己给自己打分总是偏乐观？LLM-as-a-Judge 怎么用才可信？​

答案

核心结论:

「让 Agent 自己给自己打分」几乎总是偏乐观，原因不是模型「不会评价」，而是评价者与被评价者共享了同一个生成过程的乐观倾向——模型在生成答案时倾向于产出自洽、完整、听起来正确的回答，当它再回头评价这段回答时，会把这套「看起来对」的叙事一起采信。已发表的同类工作也观察到 LLM 评估器存在对「长度更长、格式更完整、语气更自信」等表面特征的偏好，以及对自身生成内容（self-preference）的系统性高估。

四条让 Judge 可信的做法：

  1. 优先用确定性判据替代模型判分：Schema 校验、单元测试、工具调用序列断言、必需的引用是否真实存在——这些能判的绝不交给模型；
  2. 换模型当 Judge：Judge 用与被测不同的模型（最好是更强的模型），避免自我偏好；
  3. 打散并校准：用一批人工已标注的样本校准 Judge，把 Judge 的分数与人工分数做相关性对齐，并据此调整阈值与 Rubric；
  4. 用「反驳优先」而非「打分优先」的判据：让 Judge 先尝试证伪（找出反例），只有在证伪失败时才判通过；把「找茬」作为默认动作比「打分」更抗乐观偏差。

工程上必须同时记录的两件事：Judge 分数不等于质量，它是相对排序信号；门禁阈值应基于校准后的分布设定，而不是拍脑袋定「4 分及格」。

原理解析:

1. 乐观偏差从哪来

2. Judge 适合与不适合的判据

判据类型例子适合交给 Judge 吗
结构可判定JSON 是否符合 Schema、必需字段是否齐全❌ 用代码判
结果可执行验证生成的代码是否通过单测、SQL 是否能跑通❌ 用执行器判
引用可核实引用的文件路径与行号是否存在、内容是否对得上❌ 用程序核验
语义质量回答是否切题、语气是否得体、方案是否完整✅ 这才是 Judge 的战场
事实准确性（开放域）结论是否与权威源一致⚠️ 必须提供证据切片，且优先用检索核验

3. 校准怎么做

校准的本质是用人工标注的锚点集，求 Judge 分数与人工分数的映射关系：

  • 取一批（通常 50~200 条）有争议或失败倾向的样本，人工打权威分；
  • 让 Judge 对同一批打分，算两者的一致性（Spearman 相关、或按阈值算一致率）；
  • 一致性不足时，先改 Rubric 与判据描述，再考虑换 Judge 模型；改完重新校准；
  • 校准结果固化成「分数区间 → 真实质量」映射，门禁阈值按映射后的分布设定，而不是沿用 Rubric 里的原始分数。

4. 「Agent 反复失败时工程师该做什么」的分工原则

不要让 Agent 无限自我重试。正确做法是分级收敛：先分类失败（可重试 / 需换策略 / 需人工），可重试走带抖动的退避；需换策略的交给「重规划」环节并限制重规划次数；仍失败就上报并保留完整轨迹。工程介入的信号是「同一失败模式重复出现 N 次」或「重试成本超过人工介入成本」。

规范实现:

// llm-judge.ts
export interface JudgeVerdict {
  rejected: boolean;
  counterExample?: string;   // 证伪优先：必须给出可复现的反例
  rationale: string;
  confidence: 'low' | 'medium' | 'high';
}

export async function judgeWithFalsification(
  output: unknown,
  rubric: string,
  llm: (prompt: string) => Promise<string>,
  calibrate?: { anchorScore: number; judgeScore: number }
): Promise<JudgeVerdict> {
  // 1) 先跑确定性判据，能判的不交给模型
  const deterministic = await runDeterministicChecks(output);
  if (deterministic.hardFail) {
    return { rejected: true, rationale: `确定性校验未通过：${deterministic.reason}`, confidence: 'high' };
  }
  // 2) 反驳优先的 Prompt：默认动作是找反例，而不是给分
  const raw = await llm([
    '你的默认动作是尝试证伪下面这段输出，而不是为它打分。',
    '只有在明确找不到反例时，才判定为通过。',
    '输出格式：REJECTED / ACCEPTED，以及理由；若 REJECTED 必须给出可复现的反例。',
    '评分细则：' + rubric,
    '待评输出：' + JSON.stringify(output)
  ].join('\n'));
  const rejected = /^REJECTED/i.test(raw.trim());
  // 3) 校准：把 Judge 分数映射回真实质量区间
  const confidence = calibrate
    ? calibrateConfidence(calibrate.anchorScore, calibrate.judgeScore, raw)
    : 'medium';
  return { rejected, rationale: raw.slice(0, 500), confidence };
}

function calibrateConfidence(anchor: number, judged: number, raw: string): JudgeVerdict['confidence'] {
  const gap = Math.abs(anchor - judged);
  if (gap <= 0.5) return 'high';
  if (gap <= 1.0) return 'medium';
  return 'low'; // 校准偏差大时，Judge 结论不能作为门禁依据
}

门禁策略随之调整：高置信且未被驳回的样本才允许自动放行；中低置信样本一律转人工或转更重的校验链路。这条规则比「设一个分数线」稳健得多。

大小模型怎么路由？混合路由的兜底与限流怎么设计？​

答案

核心结论:

模型路由不是「按任务难度选模型」这么一句规则就够，它是一条从成本约束出发的决策链，至少包含四层：

  1. 准入判定（Can this task use a small model?）：用规则与廉价分类器先做分流——格式抽取、分类打标、字段归一化这类有确定答案空间的任务直接给小模型；需要多步推理、需要跨文档综合、需要生成可执行代码的任务必须走大模型。
  2. 难度分级（How hard is it?）：对准入后的任务做难度打分（输入长度、检索轮数、涉及工具数、是否需要多步推理），大模型也要分级，避免「一律大模型」。
  3. 兜底策略（What if the small model fails?）：小模型必须带自评/校验——结构化输出用 Schema 校验，代码用编译与单测，事实性结论用检索核验；校验不通过就升级到大模型，而不是直接返回错误给用户。升级是一次显式的重试，不是静默降级。
  4. 限流与熔断（Can we afford it right now?）：大模型是稀缺资源，必须有配额、排队与熔断；大模型超预算或超时，要能返回「部分结果 + 明确说明」，而不是让整个链路挂死。

核心原则：路由的目标不是「省 token」，而是「在质量不塌的前提下把平均成本压下来」。 只按成本路由、不带质量校验的混合路由，会在长尾任务上悄悄降级，用户感知是「这个产品最近变傻了」。

原理解析:

1. 决策链

2. 为什么「小模型校验失败就升级」是必需的

小模型在有确定答案空间的任务上非常可靠（抽取、分类、改写），在开放推理上会明显衰减。如果没有校验就直出，用户看到的是随机的高质量与低质量混杂。引入校验后，小模型承担可被验证的窄任务，大模型承担不可被验证的宽任务，二者的边界由「能不能验证」而不是「难不难」划定。

3. 限流器为什么必须与路由配套

大模型调用有硬性容量上限。若路由把流量在高峰时段大量打到小模型（因为它便宜），小模型被压垮后大量升级到已超配的大模型，反而形成级联雪崩。因此限流要放在升级路径之前：升级请求要走独立的配额与排队；超过预算时宁可返回部分结果并标注，也不要无限重试。

4. 路由效果必须被度量

路由质量有两个独立指标，缺一不可：

  • 升级率（Escalation Rate）：小模型被校验拦下并升级的比例。太低说明校验形同虚设（小模型错误被放行）；太高说明路由把小模型用在了不该用的地方，白花了两次成本。
  • 分级准确率（Routing Accuracy）：正确的任务是否被送到了正确的模型层级。这需要人工标注的锚点集来校准。

规范实现:

// model-router.ts
export type Tier = 'small' | 'large';

export interface RouteRequest {
  taskType: 'extract' | 'classify' | 'rewrite' | 'reason' | 'code' | 'multi-doc-synthesis';
  inputTokens: number;
  toolCount: number;
  retrievalRounds: number;
  hasDeterministicAnswer: boolean;
}

export interface RouteDecision {
  tier: Tier;
  reason: string;
  fallback?: Tier; // 校验失败后的升级目标
}

// 1) 准入 + 难度：先问「能不能验证」，再问「难不难」
export function decide(req: RouteRequest): RouteDecision {
  const deterministicTypes = ['extract', 'classify', 'rewrite'];
  if (deterministicTypes.includes(req.taskType) && req.hasDeterministicAnswer) {
    return { tier: 'small', reason: '答案空间确定，可由 Schema/规则校验', fallback: 'large' };
  }
  const hard = req.inputTokens > 4000 || req.retrievalRounds > 2 || req.toolCount > 3 || req.taskType === 'multi-doc-synthesis';
  if (hard) {
    return { tier: 'large', reason: '开放推理或跨文档综合，校验不可行' };
  }
  return { tier: 'small', reason: '封闭任务且复杂度可控', fallback: 'large' };
}

// 2) 校验：能确定性判定的，绝不放行未验证结果
export async function executeWithEscalation(
  req: RouteRequest,
  call: (tier: Tier) => Promise<unknown>,
  verify: (out: unknown) => Promise<{ ok: boolean; reason?: string }>,
  budget: { escalationsLeft: number; largeQuotaLeft: number }
): Promise<{ output: unknown; tier: Tier; escalated: boolean; partial?: boolean }> {
  const d = decide(req);
  let tier = d.tier;
  const out = await call(tier);
  const v = await verify(out);
  if (v.ok) return { output: out, tier, escalated: false };

  // 3) 校验失败：显式升级（受升级预算与大模型配额双重约束）
  if (d.fallback && budget.escalationsLeft > 0 && budget.largeQuotaLeft > 0) {
    budget.escalationsLeft -= 1;
    budget.largeQuotaLeft -= 1;
    const big = await call('large');
    const vb = await verify(big);
    if (vb.ok) return { output: big, tier: 'large', escalated: true };
    return { output: big, tier: 'large', escalated: true, partial: true };
  }
  // 4) 兜底：明确标注缺口，而不是静默返回错误
  return { output: out, tier, escalated: false, partial: true };
}

配套的观测指标：按任务类型统计升级率、升级后成功率、单位任务成本、P99 时延。路由策略的任何调整都应在这四个指标上同时评估——只看成本会牺牲质量，只看质量会失去路由的意义。

工具定义把上下文窗口占满了：20 个工具每个都要写描述和示例，prompt 过长怎么办？​

答案

核心结论:

  1. 工具定义是静态成本：不管这一轮用不用得上，整份工具描述都要进上下文窗口。工具一多，token 先被吃光；更糟的是工具一多模型选错的概率反而上升——描述之间语义重叠（update_record / upsert_record / save_data）、注意力被稀释。MCP 2026-07-28 客户端最佳实践的原话是：把全部工具定义前置塞进上下文会「wastes tokens, increases latency, and degrades model performance」。所以"把描述写短"不是解法，"换个时机让工具进上下文"才是。

  2. 正解是渐进式发现（Progressive Discovery）：上下文里只常驻一个轻量元工具 search_tools，模型先用自然语言搜；命中后才按需把那一个工具的完整 schema 拉进来。

  3. 三层契约要背下来：Catalog（search_tools 只返回工具名 + 一句话描述）→ Inspect（get_tool_details 返回单个工具的完整 inputSchema / outputSchema）→ Execute（带完整 schema 调工具）。关键是把"选工具"和"填参数"拆成两步：选择只需语义匹配，填参数才需要 schema，原来两者挤在同一份全量列表里。

  4. 切换要有阈值，别一刀切：规范建议以上下文窗口的 1%~5% 为界——工具定义占比低于 1% 时全量加载完全没问题，超过 5% 就应该切。

  5. 目录层的召回策略要选：关键词（BM25 / 正则）、向量（Embedding 相似度）、子 Agent（小模型代选）、混合。OpenAI 与 Anthropic 均已提供原生 tool search，优先用平台能力。

原理解析:

1. 先把成本算清楚

20 个工具、平均每个定义 400 token，合计约 8000 token，在 128K 窗口里占 6%，尚可忍受。200 个工具就是 8 万 token，占掉 6 成窗口——留给对话历史、检索结果和推理链的空间被挤没了。所以"工具多"在工程上等价于"上下文预算被静态资产吃掉"。

2. 渐进式发现的三个动作

注意 A 这一步是照常调用 tools/list 的，只是把注入时机推迟了。协议层没变，变的是 Host 的注入策略——这正是它能作为"客户端最佳实践"而非"协议变更"的原因。

3. 实现时四条必须遵守的准则（规范原文给出的）

准则做法原因
提供多个详情层级允许模型在「仅名字」「名字+描述」「完整 schema」之间选简单查询不必付 schema 的钱
缓存工具定义Host 侧 memoize，重新注入时不必再发一次 tools/list省往返；注意这是 Host 侧缓存，与模型上下文里有没有它是两件事
收到 list_changed 就重建索引服务端发 notifications/tools/list_changed 时重扫目录否则模型永远搜不到新工具
按服务器分组暴露工具让模型知道哪些能力来自同一个 server同源工具往往可组合调用

4. 最容易被忽略的坑：渐进式发现会打断 Prompt Caching

多数厂商缓存的是 prompt 前缀，而 tools 数组就在前缀里。对话中途增删工具定义会让这个缓存失效，一次 cache miss 重新计费，可能比省下的工具定义 token 还贵。规范给出的两条保命做法：

  • 把新发现的工具定义追加在缓存断点之后，不要重新排序整个 tools 数组；
  • 或者所有调用都走一个固定的 call_tool({ name, args }) 元工具，让数组从头到尾不变。

这条是区分度最高的地方——只答"用 search_tools 按需加载"的候选人，会在生产上被缓存击穿打脸。

5. 两个模式，别只知道一个

规范在同一页还给了第二种模式：程序化工具调用（Programmatic Tool Calling，也叫 Code Mode）。直接工具调用时，每次工具调用都是一次往返，链式任务（读文档 → 转换 → 写到别处）的每一个中间结果都要过一遍模型，即使它对最终产出毫无信息量。Code Mode 让模型写代码去调工具，代码在沙箱里执行，只有最终结果回到模型。代价是客户端必须实现沙箱环境。规范另有 "Combining Both Patterns" 一节讲两者如何叠加。

6. 状态：这是社区最佳实践，不是协议强制

MCP 2026-07-28 把上述内容写在客户端最佳实践文档里；MCP 社区另设 Progressive Disclosure 工作组，其章程明确声明本组无权批准规范变更，只把 grouping / tool-search / code-mode 列为候选的组织策略方向。因此准确的说法是"MCP 社区正在往这个方向收敛，2026-07-28 的客户端最佳实践已给出可落地的三层范式"，不能写成"MCP 规范已经定义了 tool search"。

// 1) 目录层：只暴露一个元工具，返回名字 + 一行描述，绝不返回 schema
interface ToolBrief { name: string; description: string }

async function searchTools(query: string, catalog: ToolBrief[]): Promise<ToolBrief[]> {
  // 生产环境应换成 BM25 / Embedding / 小模型代选，这里用关键词打分示意
  const tokens = tokenize(query)
  const score = (t: ToolBrief) =>
    tokens.reduce((s, w) => s + (t.name + ' ' + t.description).includes(w) ? 1 : 0, 0)
  return catalog
    .filter(t => score(t) > 0)
    .sort((a, b) => score(b) - score(a))
    .slice(0, 5)
    .map(t => ({ name: t.name, description: t.description }))
}

// 2) 检查层：命中后才拉完整 schema，一次只拉一个
async function inspectTool(name: string, registry: Map<string, ToolDefinition>): Promise<ToolDefinition> {
  const def = registry.get(name)
  if (!def) throw new Error('unknown tool: ' + name)
  return def
}

// 3) 切换阈值：工具定义占上下文窗口超过 1% 就考虑开启，超过 5% 应当开启
function shouldUseProgressiveDiscovery(tokenBudget: number, toolDefTokens: number): boolean {
  return toolDefTokens / tokenBudget > 0.01
}

// 4) 缓存保命：所有调用走固定元工具，tools 数组永远不变
async function callTool(name: string, args: unknown, executor: ToolExecutor): Promise<unknown> {
  return executor.invoke(name, args)
}

    • 答题切入点: 看工具选择准确率（有没有提升）、单轮平均工具定义 token（成本有没有降）、目录层首轮命中率、缓存命中率。隐藏成本必须主动提：中途增删工具定义会让 prompt 前缀缓存失效，一次 cache miss 可能比省下的 token 还贵，所以要么追加在缓存断点之后，要么走固定 call_tool 元工具让数组不变。

BLEU、ROUGE 这类 n-gram 指标为什么不能用来评 LLM 的生成？什么场景才轮到 NDCG？​

答案

核心结论:

  1. BLEU / ROUGE 本质是"参考答案的 n-gram 重合度"：BLEU 算的是截断后的 n-gram 精确率再乘长度惩罚，ROUGE 算的是 n-gram / 最长公共子序列的召回导向重合度。它们衡量的是"词面有没有对上"，不是"意思对不对"。

  2. 对 LLM 开放生成，系统性失真：正确表达方式近乎无限（换序、换同义词、换句式）。只要语义等价就该给高分，但 n-gram 指标会系统性低估，且不具单调性——把一个正确答案换个说法，分数会掉；把一个错误答案抄上参考里的几个词，分数反而会涨。它衡量的是"像不像参考译文"，不是"对不对"。

  3. BLEU 还有"精确率诅咒"：候选越多，长度惩罚越重，生成长度被迫贴近参考长度。用 BLEU 优化会逼模型写出短答案、复用参考句式。

  4. NDCG 是排序指标，回答的是"顺序对不对"：它把分级相关性按位置折扣累加（越靠前的相关文档权重越大），再除以理想排序下的最大增益做归一化。只有当你的任务本质是排序 / 检索（RAG 召回排序、搜索、推荐）时，NDCG 才是对的选择；拿它评自由文本生成是彻底用错了工具。

  5. 选型口诀：

    • 开放生成（对话、摘要改写、Agent 回答）→ 语义相似度 / LLM-as-a-Judge / 规则断言
    • 分类与抽取 → Precision / Recall / F1
    • 排序与检索 → NDCG / MRR / Recall@k
    • 翻译、摘要（有唯一参考译本）→ BLEU / ROUGE 仍是行业标准，别为了"新"而弃用

原理解析:

1. 三个指标的公式与适用面

指标定义回答的问题典型出处
BLEUBP × exp(Σ w_n · log p_n)，p_n 为截断后的 n-gram 精确率，BP 为长度惩罚我的译文与参考译文有多"像"Papineni 等，ACL 2002，pp. 311–318
ROUGE-N / ROUGE-Ln-gram 命中率 / 最长公共子序列命中率，偏召回摘要与参考摘要共享了多少内容Lin，Text Summarization Branches Out，2004
NDCG@kDCG@k / IDCG@k，DCG@k = Σ (2^rel_i − 1) / log2(i + 1)相关文档排得靠不靠前Järvelin & Kekäläinen，ACM TOIS 20(4), 2002, pp. 422–446

2. 为什么它们对 LLM 失真——三个具体的失效场景

  • 同义改写被扣分："请把订单状态改成已发货" vs "请将订单状态置为已发货"，语义完全相同，p_n 明显下降。
  • 复述参考能刷分：生成内容里塞进参考里的几个高频 n-gram，BLEU 上升，但答案可能根本是错的。精确率可以被"抄"出来，信度很低。
  • 长度惩罚反向激励：候选参考有 5 个版本时，短答案的 BP 惩罚最重，评测体系会悄悄把模型训练成"惜字如金"。

3. NDCG 何时正确、何时错误

NDCG 建立在两个假设上：高相关文档放在前面更有用；高相关文档比边缘相关文档更有用。因此它需要分级相关性标注（rel_i 通常是 0~3 的人工打分），并且只在"有唯一正确排序"的任务上成立。

  • 正确用法：RAG 召回后重排的结果好不好、搜索结果排序好不好、推荐列表好不好。
  • 错误用法：给一段自由文本算 NDCG——因为没有"位置"可言，rel_i 无从定义。

4. 一个容易答错的追问：Recall@k 和 NDCG@k 怎么选

  • 每个 query 只有一个正确文档（比如"找出这个工单编号对应的记录"）→ 用 Recall@k / Hit@k 和 MRR，NDCG 退化没有意义。
  • 每个 query 有多个相关文档且要管顺序（比如"找出所有相关的合同条款并按相关度排序"）→ 用 NDCG@k，因为它同时惩罚漏召回和排错序。
  • k 的选择不是越大越好：k 拉大能提 Recall，但 precision 下降、且召回进来的噪声会污染生成上下文。召回与精排要解耦——这正是 Rerank 存在的理由。

5. 面试官真正想听的结论

不是"BLEU 不好用"，而是：BLEU 假设存在唯一参考译文，LLM 开放生成不满足这个前提。所以在 LLM 时代不是废除 BLEU/ROUGE，而是按任务类型选指标——有唯一参考译文的封闭任务（机器翻译、部分摘要基准）继续用它们，且承认其作为"快速回归指标"的价值；开放生成必须换语义级 / 裁判级指标。

// 1) BLEU：截断精确率 + 长度惩罚（仅演示核心计算，不含 n-gram 预统计）
function bleu(candidate: string, references: string[], maxN = 4): number {
  const cGrams = ngramCounts(candidate, maxN)
  const refGrams = references.map(r => ngramCounts(r, maxN))
  const logSum = Array.from({ length: maxN }, (_, i) => {
    let clipped = 0
    for (const gram of Object.keys(cGrams[i + 1] ?? {})) {
      const maxRef = Math.max(0, ...refGrams.map(r => r[i + 1]?.[gram] ?? 0))
      clipped += Math.min(cGrams[i + 1][gram], maxRef)
    }
    const total = Object.values(cGrams[i + 1] ?? {}).reduce((a, b) => a + b, 0)
    const p = total > 0 ? clipped / total : 0
    return p > 0 ? Math.log(p) : -Infinity   // 任一阶为 0 则整体为 0
  })
  if (logSum.some(x => x === -Infinity)) return 0
  const geoMean = Math.exp(logSum.reduce((a, b) => a + b, 0) / maxN)
  const cLen = candidate.length
  const rLen = Math.min(...references.map(r => r.length))
  const bp = cLen > rLen ? 1 : Math.exp(1 - rLen / Math.max(1, cLen))
  return bp * geoMean
}

// 2) NDCG@k：分级相关性的位置折扣增益，除以理想排序增益
function ndcgAtK(rankedRel: number[], k: number): number {
  const dcg = (rels: number[]) =>
    rels.slice(0, k).reduce((sum, rel, i) => sum + (Math.pow(2, rel) - 1) / Math.log2(i + 2), 0)
  const idcg = dcg([...rankedRel].sort((a, b) => b - a))
  return idcg > 0 ? dcg(rankedRel) / idcg : 0
}

只看最终答案能判断 Agent 好不好吗？过程指标该怎么设计，PRM 和结果评测差在哪？​

答案

核心结论:

  1. 结果指标是必要但不充分的。它把一整条轨迹压成一个 0/1 或一个分数，会把本质不同的失败模式混成同一个低分：轨迹全对但最后一步拼错了，和答案蒙对了但绕了 20 步无效调用，结果指标可能都给 0。这两种失败需要的修复动作完全不同——前者是生成质量问题，后者是规划与终止问题。

  2. Agent 评测必须分两层：

    • 结果层（Outcome）：任务是否完成、最终产物是否正确；
    • 过程层（Process）：意图识别 → 工具选择 → 参数生成 → 步骤推进每一步对不对、有没有空转。 只看结果层的评测体系，没有能力定位问题出在哪一环。

  3. 过程层的标准指标集（工程上落地就这几个）：

    • 意图识别准确率——用户到底想干什么，判对没有；
    • 工具选择准确率（Top-1 / Top-k）——在候选工具里有没有挑对；
    • 参数正确率——工具挑对了，参数填对没有；
    • 无效步骤率——空转、重复调用同一工具、越权重试的比例；
    • 平均工具调用轮数 / 步数——效率；
    • 恢复率——工具报错后能否自己换路走通（这条最能区分"接了 API 的脚本"和"Agent"）。

  4. PRM（Process Reward Model，过程奖励模型）把打分位置从"最后一步"挪到了"每一步"。出自 Lightman 等 2023 年 5 月的《Let's Verify Step by Step》（arXiv:2305.20050）：论文发现过程监督在 MATH 上显著优于结果监督，过程监督模型在 MATH 测试集的一个代表性子集上解出 78% 的题，并开源了 PRM800K——80 万条步骤级人工反馈标注。

  5. 实践落点：绝大多数团队不会去训 PRM，但**"看轨迹"的能力必须做出来**。做法是：用预期工具调用序列与实际轨迹做步骤级对齐，配合规则断言和 LLM-as-a-Judge 混合打分，得到可回归的步骤级指标。

原理解析:

1. 结果指标与过程指标的能力边界

2. 同一批失败，两种结论

失败轨迹结果层得分过程层能否定位
工具选对、参数填对、最后拼装错了低能——问题在生成/汇总
意图判错，后面 8 步全在错方向上跑低能——问题在意图识别
工具反复返回空结果，Agent 重试 6 次后放弃低能——问题在终止条件
兜底逻辑恰好蒙对了答案高能——这是"高分但不可信"，结果层完全看不见

最后一行是结果指标最危险的盲区：成功率和真实能力脱钩。

3. PRM 与 ORM（结果奖励模型）的本质差异

维度ORM（结果监督）PRM（过程监督）
监督信号位置只在最终答案每一步推理 / 每个动作
监督粒度1 条 / 任务步骤级，PRM800K 达 80 万条
信号稀疏性极稀疏（对错二元）稠密（每步都有标签）
归因能力差——错了不知道为什么错强——能定位到具体一步
标注成本低高（这也是 PRM800K 的价值所在）

必须说清的边界：Lightman 等人的结论是在数学推理任务上得出的（过程监督训练出的模型在 MATH 上优于结果监督），不能直接外推成"所有业务 Agent 都该上 PRM"。在企业 Agent 场景里，PRM 的方法论（把监督/评测下沉到步骤级）比模型本身有用得多。

4. 步骤级评估器怎么实现

思路是把预期轨迹当成一个"剧本"，实际轨迹当成"录像"，逐幕对齐：

对齐时至少有三种偏差要分开记：漏调（该调没调）、多调（不该调调了）、错序（调了但顺序不对）。把这三类分开统计，才能指导修复。

5. 离线评测与线上监控的分工

  • 离线：用固定评测集跑过程级指标，纳入 CI 做回归门禁——改 Prompt、改模型、改工具描述都可能悄悄拉低工具选择准确率。
  • 线上：过程指标多数无法实时判定（要等轨迹跑完），只能做延迟聚合（按会话或任务结束后回灌），但必须保留原始轨迹，否则线上问题无法复盘。

6. 为什么过程指标必须与确定性断言混用

纯 LLM-as-a-Judge 打过程分，会重复"偏乐观"的老问题。更稳的分层是：

  • 硬断言（能用规则判的绝不放给 Judge）：工具名是否在允许列表内、必填参数是否齐全、输出是否符合 Schema、是否触发了高风险工具；
  • 语义分（Judge 承担）：这一步的思考与动作是否与意图匹配；
  • 人工锚点（校准 Judge）：定期用人工标注集反查 Judge 的打分偏差。

规范实现:

interface TrajectoryStep {
  kind: 'intent' | 'tool_call' | 'final'
  toolName?: string
  args?: Record<string, unknown>
}

interface ProcessMetrics {
  intentAccuracy: number
  toolSelectionTop1: number
  toolSelectionTopK: number
  argumentAccuracy: number
  wastedStepRatio: number
  avgToolCalls: number
  recoveryRate: number
}

// 步骤级对齐：把预期剧本与实际轨迹逐幕比对，分开记漏调 / 多调 / 错序
export function alignTrajectory(
  expected: TrajectoryStep[],
  actual: TrajectoryStep[]
): { missed: string[]; extra: string[]; reordered: boolean } {
  const expectedTools = expected.filter(s => s.kind === 'tool_call').map(s => s.toolName ?? '')
  const actualTools = actual.filter(s => s.kind === 'tool_call').map(s => s.toolName ?? '')
  const missed = expectedTools.filter(t => !actualTools.includes(t))
  const extra = actualTools.filter(t => !expectedTools.includes(t))
  const common = actualTools.filter(t => expectedTools.includes(t))
  const expectedOrder = expectedTools.filter(t => common.includes(t))
  const reordered = common.join('|') !== expectedOrder.join('|')
  return { missed, extra, reordered }
}

// 硬断言走规则，软语义分才交给 Judge
export function scoreTrajectory(
  expected: TrajectoryStep[],
  actual: TrajectoryStep[],
  allowedTools: Set<string>
): ProcessMetrics {
  const expTools = expected.filter(s => s.kind === 'tool_call')
  const actTools = actual.filter(s => s.kind === 'tool_call')
  const hitTop1 = actTools.length > 0 && expTools[0]?.toolName === actTools[0].toolName
  const hitTopK = expTools.some(e => actTools.some(a => a.toolName === e.toolName))
  const { missed, extra } = alignTrajectory(expected, actual)
  const legal = actTools.every(a => allowedTools.has(a.toolName ?? ''))
  return {
    intentAccuracy: expected[0]?.kind === 'intent' ? (actual[0]?.kind === 'intent' ? 1 : 0) : 1,
    toolSelectionTop1: actTools.length ? (hitTop1 ? 1 : 0) : 0,
    toolSelectionTopK: hitTopK ? 1 : 0,
    argumentAccuracy: actTools.length ? (legal ? 1 : 0) : 0,
    wastedStepRatio: actTools.length ? extra.length / actTools.length : 0,
    avgToolCalls: actTools.length,
    recoveryRate: missed.length === 0 ? 1 : 0,
  }
}

答案

核心结论:

  1. A2A = Agent2Agent Protocol，一个开放标准，目标是让不同厂商、不同框架（LangGraph、CrewAI、Semantic Kernel 或自研）实现的 Agent 互相协作。官方定位是「agent 之间的通用语言」。协议由 The Linux Foundation 托管（Apache 2.0 许可），官方站点公告显示 A2A 已加入 Agentic AI Foundation。

  2. 与 MCP 的分工，一句话记住：MCP 把每个 Agent 连到它自己的工具；A2A 把 Agent 与 Agent 连起来。 官方文档专设「A2A and MCP」一节说明两者互补：外部用 A2A 与别的 Agent 对话，内部用 MCP 调自己的工具与资源。官方给的「汽车修理厂」类比里，顾客↔店经理、店经理↔机械师、机械师↔配件供应商都是 A2A，而机械师调「诊断扫描仪」「维修手册库」是 MCP。

  3. 传输与格式：走 HTTP(S)，所有请求与响应的载荷格式统一为 JSON-RPC 2.0，典型方法名是 SendMessage；媒体类型注册为 application/a2a+json，版本协商走 A2A-Version 请求头（扩展协商走 A2A-Extensions）。

  4. 五个核心对象：

    • Agent Card：一份 JSON「数字名片」，声明身份、服务端点 URL、A2A 能力、认证要求与技能列表，是发现与建连的入口；
    • Message：一次交互回合，带 role（user 或 agent）与唯一 messageId，内含若干 Part；
    • Part：内容容器，用 oneof 结构恰好承载一种内容——text（纯文本）/ raw（内联二进制）/ url（外部引用）/ data（结构化 JSON），可另带 mediaType、filename、metadata；这个设计让协议天然与模态无关；
    • Artifact：任务产出的具体交付物，有唯一 artifactId、可读名称与一个或多个 Part，可增量推流；
    • Task：有生命周期的任务对象，含 id、contextId、status.state 与 artifacts。

  5. 三种交互机制：Request/Response（长任务靠轮询）、SSE 流式（客户端开长连接拿增量结果与状态更新）、Push Notification（服务端在重要更新时回调客户端提供的 webhook，适合超长任务与断连客户端）。

  6. 上下文靠 contextId 串联：由服务端生成，把一组相关 Task 归到同一上下文，后续交互靠它延续——这正是「多轮委派」在协议层的落点。

  7. 安全边界值得单独强调：A2A 的设计目标之一是 Opaque（不透明）——Agent 之间协作不需要暴露内部记忆、工具与专有逻辑；认证要求写在 Agent Card 里，凭据（OAuth token、API key）走 HTTP 头，与协议消息本身分离。

  8. 必须说清的边界：

    • 规范仍在演进：当前发布版为 1.0.0（历史版本 0.3.0 / 0.2.6 / 0.1.0）。v1.0 是一次破坏性变更，规范附录 A.2 明确列出两项：移除了多态对象的内联 kind 判别符（影响 Part 类型与流式事件类型——v0.3.x 靠 "kind": "text" 这类内联字段区分对象类型）、Extended Agent Card 字段被迁移。版本协商靠 A2A-Version 请求头；请求的版本不被支持时返回 400，响应体是 application/problem+json 并附带 supportedVersions 数组。说「A2A 已定稿不会变」是错的；
    • Artifact 的版本串联（哪个产物是哪个产物的修订版）不属于规范——官方明确「服务端 Agent 不应跟踪产物变更，客户端才是合适的位置」；这是很容易被答错的细节；
    • A2A Server 可以把部分技能同时暴露为 MCP 兼容资源，但这只是便利能力，不改变两者的主分工。

原理解析:

1. 两个协议的层次关系

2. 一次委派任务的完整生命周期

关键点：服务端返回的是 Task 还是 Message，取决于任务是否长时运行——长任务回 Task（即时回 Message）。input-required 是一个明确的状态：Agent 遇到歧义时用它向客户端要信息，而不是自己瞎猜。

3. 对象职责速查

对象作用谁生成
Agent Card能力自描述与发现入口服务端
Message一次交互回合（角色 + 内容）双方
Part单个内容单元，oneof 承载一种载荷双方

规范实现:

下面是客户端侧的最小骨架：读 Agent Card 做能力判断，发 SendMessage，并区分「回 Task」与「回 Message」两种响应形态：

// a2a-client.ts —— A2A 客户端最小骨架
export interface AgentCard {
  name: string
  url: string // 服务端点
  capabilities: string[]
  skills: { id: string; description: string }[]
  securitySchemes?: Record<string, unknown>
}

export interface A2APart {
  // oneof：恰好承载一种内容
  text?: string
  raw?: string // base64 内联二进制
  url?: string
  data?: Record<string, unknown>
  mediaType?: string
  filename?: string
  metadata?: Record<string, unknown>
}

export interface A2ATask {
  id: string
  contextId: string
  status: { state: string } // working / input-required / completed ...
  artifacts?: { artifactId: string; name: string; parts: A2APart[] }[]
}

export type A2AResponse = { task: A2ATask } | { message: { role: string; messageId: string; parts: A2APart[] } }

export async function sendMessage(
  card: AgentCard,
  text: string,
  contextId?: string
): Promise<A2AResponse> {
  const payload = {
    jsonrpc: '2.0',
    id: 'req-001',
    method: 'SendMessage',
    params: {
      message: {
        role: 'user',
        messageId: `msg-${Date.now()}`,
        contextId, // 续接同一上下文时带上
        parts: [{ text }]
      }
    }
  }
  const res = await fetch(card.url, {
    method: 'POST',
    headers: {
      'content-type': 'application/a2a+json',
      // 版本协商：当前发布版 1.0.0；版本不支持时服务端回 400 + supportedVersions
      'a2a-version': '1.0.0',
      // 凭据走 HTTP 头，与协议消息分离
      authorization: `Bearer ${process.env.A2A_TOKEN ?? ''}`
    },
    body: JSON.stringify(payload)
  })
  const body = await res.json()
  // 长任务回 task，即时回复回 message
  return body.result as A2AResponse
}

工程上最容易漏的两点：凭据必须走请求头而不是塞进消息体（这是协议明确的设计）；续接多轮任务必须回传 contextId，否则服务端无法把新 Task 归到同一上下文。

Agent 到底怎么判断该用哪个 Skill？怎么设计测试集来度量这个路由准不准？​

答案

核心结论:

  1. Agent 并没有一个「路由函数」。按 Agent Skills 官方规范，Skill 通过**渐进式披露（progressive disclosure）**被加载，分三段：Discovery（启动时只加载每个 skill 的 name 与 description，「刚好够判断什么时候可能相关」）→ Activation（任务与某份 description 匹配时，才把完整的 SKILL.md 读进上下文）→ Execution。因此 description 承担了全部的触发责任——描述写不准，该用时不加载、不该用时乱加载，后面的指令写得再好也没用。

  2. 所以要测的是「该不该被触发」，而不是「触发了做得好不好」。这是两个必须分开的评测对象：前者是路由准确率（二分类问题，可量化、可卡 CI 门禁），后者是输出质量（需要 eval 驱动的迭代）。Agent Skills 官方文档也正是把这两件事拆成了两篇独立的指南。

  3. 触发评测集怎么造（官方口径）：

    • 规模约 20 条：810 条 should-trigger + 810 条 should-not-trigger；
    • 负例必须是近似命中（near-miss）——与 skill 共享关键词或概念、但实际需要另一套能力；用明显无关的句子充数等于没测；
    • 正例要沿多个轴铺开：措辞（正式 / 口语 / 带错别字）、显式性（点名领域 vs 只描述需求）、细节量（一句话 vs 带路径与列名的长描述）、复杂度（单步 vs 多步且技能埋在链路中间）；
    • 要有真实感：真实用户提示里有文件路径、个人背景、具体列名与公司名、口语与缩写。

  4. 怎么判定「通过」：模型行为是非确定性的，同一句话这次触发、下次不触发，所以每条查询跑多次（官方建议 3 次起）并计算 trigger rate（触发比例）。should-trigger 的通过条件是 trigger rate 高于阈值（官方给的起点是 0.5），should-not-trigger 则要求低于该阈值。

  5. 怎么量化：本质是二分类，因此要同时看两个方向的错误：

    • 漏触发（should-trigger 却没加载）→ 能力直接缺失；
    • 误触发（should-not-trigger 却加载了）→ 代价通常更高：白烧上下文、误导后续流程、可能连带触发不相关的危险工具。
    • 另外必须做 train / validation 划分：对着全部评测集优化 description 会过拟合，得到「只在这 20 句上准」的假象。

  6. 工程落点：改 skill 的 description 等于一次 prompt 级变更，必须过触发回归；新增 skill、改写描述、调整 skill 集合都要重跑全量触发评测。触发准确率是可以量化、可以写进流水线门禁的指标——这与「输出质量还在摸索阶段」是两回事。

  7. 必须说清的边界：

    • 官方规范对 description 有 1024 字符的硬上限——描述写得又长又泛，既挤占启动期上下文，也让触发判定更模糊；
    • 官方明确指出：Agent 通常只会为「超出自身能力范围」的任务去考虑 skill。像「读一下这个 PDF」这种它自己能做的简单请求，即使 description 完全匹配也可能不加载——这是正常行为，不应记成漏触发；
    • 触发准确率 ≠ 工具调用准确率（tool 由模型直接发起，skill 走渐进式披露）；也 ≠ RAG 知识库路由准确率（那是另一条链路）。

原理解析:

1. 渐进式披露的三段与各自的失败模式

2. 两类错误的代价不对称

错误类型触发条件后果治理手段
漏触发should-trigger 未达阈值专用能力没被用上，Agent 用通用方式硬扛扩正例覆盖轴；description 增加适用上下文
误触发should-not-trigger 高于阈值加载无关 SKILL，占上下文、误导流程写近似命中负例；description 写清「不适用」边界
输出质量差触发对了但做不好结果不符预期属于输出质量评测，不在本题范围
阈值设置错用错阈值误触发率被系统性放大按业务代价调阈值，误触发代价高则上调

3. 为什么必须跑多次

模型采样有随机性，同一份 prompt 两次可能给出不同选择。单次结果测的是运气，不是路由准确率。多次运行 + trigger rate 把「偶然」摊平成一个稳定的比例指标，才能作为门禁信号。

规范实现:

下面是最小可用的触发评测器：读入带 should_trigger 标注的查询集，跑多次取触发率，按阈值判定通过。

interface TriggerQuery {
  query: string
  should_trigger: boolean
}

interface TriggerRunResult {
  query: string
  should_trigger: boolean
  triggered: boolean
  runs: number
  trigger_rate: number
  passed: boolean
}

export interface TriggerEvalOptions {
  queries: TriggerQuery[]
  runs?: number          // 官方建议 3 次起
  threshold?: number     // 官方起点 0.5
  // 由具体 Agent 客户端实现：判断本次运行是否加载了目标 skill
  runOnce: (query: string) => Promise<boolean>
}

export async function evalTriggering (opts: TriggerEvalOptions): Promise<{
  results: TriggerRunResult[]
  recall: number          // should-trigger 的触发率均值
  falseTriggerRate: number // should-not-trigger 的误触发率均值
  passed: boolean
}> {
  const runs = opts.runs ?? 3
  const threshold = opts.threshold ?? 0.5
  const results: TriggerRunResult[] = []

  for (const q of opts.queries) {
    let hits = 0
    for (let i = 0; i < runs; i++) {
      if (await opts.runOnce(q.query)) hits++
    }
    const triggerRate = hits / runs
    // 正例要求「触发率够高」，负例要求「触发率够低」，判据是同一个阈值的两侧
    const passed = q.should_trigger
      ? triggerRate > threshold
      : triggerRate < threshold
    results.push({
      query: q.query,
      should_trigger: q.should_trigger,
      triggered: hits > 0,
      runs,
      trigger_rate: triggerRate,
      passed
    })
  }

  const pos = results.filter(r => r.should_trigger)
  const neg = results.filter(r => !r.should_trigger)
  const recall = pos.length
    ? pos.reduce((s, r) => s + r.trigger_rate, 0) / pos.length
    : 0
  const falseTriggerRate = neg.length
    ? neg.reduce((s, r) => s + r.trigger_rate, 0) / neg.length
    : 0

  return {
    results,
    recall,
    falseTriggerRate,
    // 误触发通常比漏触发更贵，所以门禁对它的要求更严
    passed: recall > threshold && falseTriggerRate < threshold
  }
}

工程上还要补两件事：把评测集拆成 train / validation 两份，调 description 只看 train、最终结论看 validation；以及把 description 的变更纳入版本管理，因为它就是路由策略本身。

ASR 的 WER 明明降下来了，为什么下游任务的准确率反而可能下降？​

答案

核心结论:

  1. 先说清 WER 是什么：它是词级编辑距离，WER = (S + D + I) / N = (S + D + I) / (S + D + C)，其中 S 是替换数、D 是删除数、I 是插入数、C 是正确词数、N 是参考文本词数。计算方式是先做词级动态规划对齐（Levenshtein），再统计三类编辑的占比。0 表示完全正确，越小越好。

  2. WER 衡量的只是「词形序列的对齐差异」，不是「信息保真度」。官方指标卡本身就写明了它的局限：这类度量不提供错误性质的任何细节，因此仍需额外做对齐分析才能定位主要错误来源。换句话说，WER 是一个把错误「摊平」后的聚合标量。

  3. 所以「WER 降了但下游变差」是完全可能的，核心是两条：

    • 错误的「位置」远比错误的「数量」重要，而 WER 对位置完全不敏感：所有错误都集中在实体、数字、专名、否定词上时，WER 可能只降了一两个百分点，但下游（订单查询、合同字段抽取、指令执行）几乎全错；反过来，错误全落在语气词、冗余词上，WER 看着差不多，下游几乎不受影响。
    • WER 的分母 N 是每个样本自己的参考词数：同样的绝对错误数，参考文本越短 WER 越高。所以跨样本比较 WER 必须看长度分布——短句的 WER 天然波动更大，一个模型可能在长句上大幅改善、在短句上变差，聚合后被掩盖。

  4. 还有一个中文场景的实操坑：WER 依赖词边界，而中文没有天然空格分隔；分词口径不同算出来的 WER 互不可比。中文（及无空格语言）更常用的是 CER（字符错误率）。报数时必须声明用的是哪个口径。

  5. WER 该用在哪、不该用在哪：

    • 该用：同数据集、同参考、同对齐口径下做 ASR 引擎版本对比；以及做粗粒度回归门禁（不许比基线差过某个幅度）。
    • 不该用：当业务验收指标。业务在乎的是「字段抽对了吗」「意图识别对了吗」「任务完成了吗」，这些是任务相关指标，与词级编辑距离之间没有单调映射关系。

  6. 正确的做法是分层诊断，而不是盯一个数：

    • 按错误类型拆：S 高通常是同音字、专名、数字混淆；D 高通常是端点检测（endpointing）切早了、漏字；I 高通常是幻觉式补字或重复。三者的修复方向完全不同。
    • 按关键实体单独算准确率（entity accuracy）——业务真正在乎的就是这一层。
    • 直接测下游任务指标：意图准确率、字段抽取 F1、端到端任务成功率。
    • 多指标并报：WER / CER + 实体准确率 + 下游任务指标，缺一个都可能被钻空子。

  7. 必须说清的边界：WER 的前提是存在正确的参考文本（人工标注），而标注本身有噪声；自由口语、无参考场景下 WER 无从谈起。

原理解析:

1. 同一组错误，两种完全不同的下游后果

场景参考文本识别结果WER下游后果
关键实体错订单号 A12345订单号 A12346约 1/5取错订单，交易出错
语气词错我要退款谢谢我要退宽谢谢约 1/4无所谓
否定词错不要退款要退款约 1/4意图反转，行为完全相反

两行的 WER 几乎一样，业务后果差着数量级。这就是「WER 降了但下游没降（甚至更差）」的机制来源。

2. 指标分层：该盯哪一层

3. 排查顺序：WER 涨了/降了但业务没跟上，怎么查

规范实现:

下面是把「WER 变化」翻译成「业务影响」的最小分析器：按错误类型、按长度分层，并单独统计关键实体准确率。

interface AlignedToken {
  ref: string
  hyp: string
  op: 'match' | 'sub' | 'del' | 'ins'
}

export interface WerBreakdown {
  wer: number
  byOp: { sub: number; del: number; ins: number }
  /** 关键实体（数字 / 专名 / 否定词）是否被正确识别 */
  entityAccuracy: number
  /** 按参考文本长度分层后的 WER，用于发现被平均掩盖的问题 */
  werByLength: Array<{ bucket: string; wer: number; count: number }>
}

/** 从词级对齐结果算出分层指标。align 由编辑距离 DP 产出 */
export function analyze (align: AlignedToken[], opts: {
  isCriticalEntity?: (token: string) => boolean
  lengthBuckets?: Array<{ name: string; max: number }>
}): WerBreakdown {
  let sub = 0, del = 0, ins = 0, correct = 0, refWords = 0
  let entityTotal = 0, entityHit = 0

  for (const t of align) {
    if (t.op === 'match') {
      correct++
      refWords++
    } else if (t.op === 'sub') {
      sub++
      refWords++
    } else if (t.op === 'del') {
      del++
      refWords++
    } else {
      ins++
    }
    if (opts.isCriticalEntity?.(t.ref)) {
      entityTotal++
      if (t.op === 'match') entityHit++
    }
  }

  const n = refWords || 1
  const wer = (sub + del + ins) / n

  // 按长度分层，避免长短句被平均数掩盖
  const werByLength = (opts.lengthBuckets ?? []).map(b => {
    const inBucket = align.filter(t => t.ref.length > 0 && t.op !== 'ins' && t.op !== 'match'
      ? true : true) // 占位：真实实现应先按样本分组再统计
    void inBucket
    return { bucket: b.name, wer: 0, count: 0 }
  })

  return {
    wer,
    byOp: { sub, del, ins },
    entityAccuracy: entityTotal ? entityHit / entityTotal : 1,
    werByLength
  }
}

注意 entityAccuracy 与 wer 是两个独立信号：实体准确率掉而 WER 没动，就是「整体转写质量没变差，但业务关键信息被毁了」的典型形态——这类退化只盯 WER 永远发现不了。

  • 必答：能写出或准确描述 WER 的定义（词级编辑距离、S/D/I/N）；指出 WER 不反映错误性质与位置；能举出「关键实体错 vs 语气词错，WER 相同但后果相反」的例子；知道要按 S/D/I 分层、按长度分层、补实体准确率与任务指标。
  • 加分项：知道中文场景要声明词/字口径（CER vs WER）；知道 WER 分母随样本长度变化带来的比较陷阱；知道 WER 依赖人工参考文本、标注本身有噪声；能区分「回归门禁」与「业务验收」两种用法。
  • 常见误区：认为 WER 降低必然意味着体验变好；把 WER 当业务验收指标；忽略中文分词口径；认为可以通过调 WER 阈值来提升下游效果。

深度追问链:

  1. 追问 1：WER 没变但用户投诉变多了，你先查什么？
    • 答题切入点：先看错误类型分布有没有变（同样的 WER，错误可能从 D 变成 S）；再算关键实体准确率；最后做长度分层。大概率是「错误挪位置了」或「短句变差了」。
  2. 追问 2：端点检测（endpointing）调得更激进，WER 降了，用户却说经常反应慢/截断，为什么？
    • 答题切入点：WER 只统计已经输出的词，不统计「没等用户说完就切断」丢掉的词——漏在对齐之外的部分不进 WER，但直接体现为体验损失。所以要额外监控端到端延迟与截断率，别让 WER 掩盖。
  3. 追问 3：如果只能给业务方报一个数，你报哪个？
    • 答题切入点：任务级指标（意图准确率 / 字段抽取 F1 / 端到端成功率），因为业务方要的是任务结果；WER 作为研发侧的过程指标保留，用于版本对比与回归门禁。一个数不够时，报告要分层给，不能只给一个最漂亮的。
  4. 追问 4：没有人工参考文本的场景怎么办？
    • 答题切入点：WER 无从谈起；改用无参考指标（如说话人一致性、可懂度、语义相似度）与代理任务指标，并明确标注这些不是转写质量本身；不要伪造参考。

Agent 能力的公开基准该怎么选？GAIA、SWE-bench、AgentBench、WebArena 各自测的是什么？​

答案

核心结论:

  1. 这四个基准测的是四个不同维度，不是同一件事的「难度档位」，所以不存在「哪个分更高就更好」的问题。选基准的第一步是先确定要测哪个维度，第二步才是挑基准。
  2. GAIA（arXiv:2311.12983）测「通用助理的真实世界问答」：论文提出 466 道题，其中保留 300 道的答案用于排行榜（其余公开题目不含答案）。题目按工具与步数分三级——Level 1：一般不需要工具，或至多一个工具但不超过 5 步；Level 2：步数大约在 5 到 10 之间，且需要组合不同工具；Level 3：面向近乎完美的通用助理，需要任意长的执行。评测方式是短答案精确匹配（ground truth 就是 90、+4.6 这类短串）。论文强调设计目标之一是抗记忆（robustness against memorization）。
  3. SWE-bench（arXiv:2310.06770）测「真实仓库级的修 bug 能力」：2,294 个任务，取自 12 个流行 Python 仓库的真实 GitHub issue 与对应 PR；给定代码库与 issue 描述，要求模型改代码解决。验证方式是执行式验证——跑测试用例判定成败。SWE-bench Lite 是从中采样的 300 个实例子集，采样标准是「更自包含、聚焦功能性 bug 修复」，覆盖原 12 个仓库中的 11 个。
  4. AgentBench（arXiv:2308.03688）测「交互式环境里的规划与决策」：一个多维基准，由 8 个不同环境组成，评测了 29 个 API 与开源模型。论文的一个关键观察是：头部商用模型表现强，但与规模不超过 70B 的许多开源模型之间存在显著差距。
  5. WebArena（arXiv:2307.13854）测「真实网页上的端到端任务完成率」：环境是可自托管的真实网站（论文开源了实现），因此可复现。论文报告其最好的 GPT-4 系 Agent 端到端任务成功率只有 14.41%，而人类表现为 78.24%——这是「当前模型离可用还差多远」最直白的一组对照。
  6. 结论：公开榜单不能直接用来验收自己的系统。三条硬理由：① 维度不匹配——榜单分数不回答「我的业务场景行不行」；② 污染与过拟合——公开测试集会被反复用于训练与提示调优，分数会虚高；③ 口径漂移——模型、提示词、工具、脚手架、检索配置任一变化都会改分，跨时间的分数不可直接比较。
  7. 「污染」不是假设，已经被量化为实证：针对 SWE-bench 的诊断性研究给出了具体数字——在同样都是知名开源 Python 项目的前提下，模型在 SWE-Bench-Verified 上的表现比在 BeetleBox / SWE-rebench 上好 3 倍，仅凭 issue 文本定位被改过的文件这一项好 6 倍；论文的判断是「scores may reflect training recall, not issue-solving skill」。另有诊断工作用两个探针任务（仅凭 issue 描述猜文件路径、只给当前文件上下文复现 ground truth 函数）区分「可泛化的解题能力」与「学到的工件」，结论是现行评测协议可能高估了模型的真实能力。

原理解析:

1. 四个基准的定位对照

2. 为什么「拿榜单验收自己的系统」是错的

  • 维度不对齐：SWE-bench 分数高，不代表你的「内部工单处理 Agent」行不行——它连检索、权限、审批这些环节都不涉及。
  • 评测集是公开的：公开基准的题目与评分逻辑一旦公开，就可能被用于训练数据、提示词调优甚至针对评分函数做优化。这不必然是作弊，但分数的含义变了：从「能力」变成「对这套公开题的拟合度」。
  • 口径会漂：SWE-bench 官方自己就给了完整版与 Lite 两个口径；WebArena 换了站点实现、AgentBench 换了环境版本，分数都不可直接跨版本比较。报分数必须同时报「版本 + 提示 + 脚手架 + 采样设置」。

LLM 应用上线后怎么排查问题？AI 应用的可观测性和普通 Web 服务有什么不一样，OpenTelemetry 的 GenAI 语义约定到底约定了什么？​

答案

核心结论:

  1. 可观测性仍是 Logs / Metrics / Tracing 三支柱，但重心压在 Tracing 上。普通 Web 服务「一次请求 = 一次处理」，日志里翻一翻就能定位；AI Agent 的一次请求会扇出成多次模型调用与多次工具调用，只有 trace 能还原「模型先调了什么、看到什么、再决定调什么」这条因果链——只看日志是看不到「模型决策错了」的，因为决策过程只存在于调用序列里。
  2. 不能照搬传统 HTTP 的 span 划分。一次 HTTP 请求内部藏着语义完全不同的若干段操作：对话生成、向量化、工具执行、子 Agent 调用。它们的入参出参形态、耗时分布、失败模式都不同，混在一个 HTTP span 里等于没埋。OpenTelemetry 为此定义了专门的 GenAI 语义约定，且已从主语义约定仓迁出为独立仓 open-telemetry/semantic-conventions-genai。
  3. 约定的核心是一个属性 gen_ai.operation.name，取值覆盖 chat / embeddings / execute_tool / generate_content / invoke_agent；Agent 场景另有 create_agent / invoke_agent / execute_tool 三类 span。配合 gen_ai.request.model、gen_ai.response.model、gen_ai.response.finish_reasons、gen_ai.agent.* 等属性，可以把不同厂商、不同框架产生的调用拉到同一口径下比较。
  4. Agent 要额外记录「状态」而不只是「请求」：每个节点的入参出参、State 快照、token 与成本累计、迭代轮次，才是复现一条失败轨迹的最小材料。只有 span 没有状态快照，等于知道「走过哪条路」却不知道「当时手里拿着什么」。
  5. 排查时的价值排序：先看 trace 的形状（调了几次模型、工具序列是否符合预期、耗时卡在哪一段），再看 单个 span 的属性（模型、finish_reason、token 数），最后才翻日志。先看日志是最慢的路径。

原理解析:

1. 三支柱在 AI 应用里的分工

支柱AI 场景的典型指标 / 内容回答什么问题
Tracing每次模型调用、工具调用、Agent 节点的 span 与父子关系「为什么慢 / 为什么错」——调用链形状与每段耗时
MetricsQPS、错误率、P50 / P95 / P99 延迟、token 消耗、工具调用成功率、单请求成本「整体健康吗」——趋势、告警、容量
Logs结构化 JSON，按 request_id 串联 trace 与日志「具体参数是什么」——现场细节

2. 为什么传统 HTTP tracing 不够用

维度传统 Web 服务AI / Agent 应用
一次请求的内部结构一次处理多段模型调用 + 工具调用 + 再次模型调用的扇出链
失败的主要形态5xx / 超时答案质量不合格、工具选错、循环不收敛、格式不合法
关键语义路由、状态码prompt、模型版本、finish_reason、tool_calls、token

一个直白的判据：监控面板上只有「HTTP 200 / 响应耗时」两个指标时，AI 应用实际上是裸奔的——用户抱怨「它答错了」时，你没有任何证据可看。

3. OpenTelemetry GenAI 语义约定约定了什么

  • 操作类型：gen_ai.operation.name 取值 chat、embeddings、execute_tool、generate_content、invoke_agent。
  • Agent 相关 span：独立文档定义 create_agent、invoke_agent、execute_tool 三类；属性含 gen_ai.agent.id / gen_ai.agent.name / gen_ai.agent.version / gen_ai.agent.description。
  • 记忆相关：约定里还有 gen_ai.memory.* 一组属性（memory.store.id、memory.record.id、memory.record.count、memory.query.text 等），对应「读写了哪些记忆」。
  • 模型与响应：gen_ai.request.model、gen_ai.response.model、gen_ai.response.id、gen_ai.response.finish_reasons、gen_ai.response.status；token 用量另有专门文档（gen_ai.client.token.usage 系列）。
  • 厂商与协议：仓内为各厂商与协议各有一页（OpenAI、Anthropic、AWS Bedrock、Azure AI Inference 等），并且已有 mcp.md 与 a2a.md——MCP 调用与 A2A 互操作也纳入了同一套约定。

这条最值得记的判断是：MCP 与 A2A 的 span 也在 GenAI 约定内，所以「模型调用」「工具协议调用」「Agent 间调用」三类可以在同一棵 trace 树上对齐，不需要三套埋点。

4. Agent 场景要额外记「状态」

单有 span 只能回答「走过哪条路」，回答不了「当时手里拿着什么」。可复现一条失败轨迹的最小材料是三样：① 每个节点的入参出参；② State 快照（多 Agent 系统里 State 往往是 TypedDict，节点做的是部分更新）；③ 累计量（token、成本、迭代轮次）。

实践中这三样要同一个 request_id 能串起来：trace 的 span id 记在日志字段里，日志按 request_id 索引，State 快照按 request_id + 节点名存储。

规范实现:

// 用 OpenTelemetry 语义约定给一次 Agent 运行布点
import { trace, SpanStatusCode } from '@opentelemetry/api';

const tracer = trace.getTracer('my-agent', '1.0.0');

type ToolCall = { id: string; name: string; args: unknown };

async function runAgent(userQuery: string, userId: string): Promise<string> {
  // 顶层 Agent span：对应 invoke_agent
  return tracer.startActiveSpan('invoke_agent', async (agentSpan) => {
    agentSpan.setAttribute('gen_ai.operation.name', 'invoke_agent');
    agentSpan.setAttribute('gen_ai.agent.name', 'shopping-guide');
    agentSpan.setAttribute('gen_ai.request.model', 'gpt-4o');
    try {
      const messages = [{ role: 'user', content: userQuery }];

      for (let turn = 0; turn < 8; turn++) {
        // 每一次模型调用单独一个 span：对应 chat
        const reply = await tracer.startActiveSpan('chat', async (span) => {
          span.setAttribute('gen_ai.operation.name', 'chat');
          span.setAttribute('gen_ai.request.model', 'gpt-4o');
          span.setAttribute('gen_ai.usage.input_tokens', messages.length);
          const out = await callModel(messages);
          span.setAttribute('gen_ai.response.finish_reasons', out.finishReason);
          span.setAttribute('gen_ai.response.model', out.model);
          span.setAttribute('gen_ai.usage.output_tokens', out.tokens);
          if (out.finishReason !== 'stop') span.setStatus({ code: SpanStatusCode.ERROR });
          return out;
        });

        // 没有工具调用就收尾
        if (reply.toolCalls.length === 0) {
          agentSpan.setAttribute('gen_ai.response.finish_reasons', reply.finishReason);
          return reply.text;
        }

        // 每个工具调用单独一个 span：对应 execute_tool，并挂到 Agent span 下
        for (const call of reply.toolCalls) {
          await tracer.startActiveSpan('execute_tool', async (toolSpan) => {
            toolSpan.setAttribute('gen_ai.operation.name', 'execute_tool');
            toolSpan.setAttribute('gen_ai.tool.name', call.name);
            toolSpan.setAttribute('gen_ai.tool.call.id', call.id);
            // 关键：把「工具看到的东西」记进 span，失败时才能复盘
            toolSpan.setAttribute('gen_ai.tool.call.arguments', JSON.stringify(call.args));
            const result = await runTool(call as ToolCall, userId);
            toolSpan.setAttribute('gen_ai.tool.call.result', JSON.stringify(result).slice(0, 2000));
          });
        }
      }
      agentSpan.setStatus({ code: SpanStatusCode.ERROR, message: 'max turns exceeded' });
      return '';
    } finally {
      agentSpan.end();
    }
  });
}

  • 必答：① 说清 AI 应用可观测性的三支柱，并指出重心在 trace；② 说清「一次请求扇出成多次模型与工具调用」这个结构差异；③ 报出 gen_ai.operation.name 的取值 chat / embeddings / execute_tool / generate_content / invoke_agent；④ 指出状态快照是 Agent 场景不可省的一环。

  • 常见误区：把 AI 应用的可观测性等同于「加一个 APM 插件」——通用 APM 只会把 HTTP 记录下来，看不到模型决策链；把 tracing 当成日志的替代——trace 给结构、日志给现场，两者要靠 request_id 串起来；认为「有 trace 就能复现」——没有 State 快照与入参快照，trace 只告诉你它做了什么，不告诉你它看到了什么；把 GenAI 语义约定说成是 OpenAI 专有规范——它是厂商无关的跨厂商约定。
